# Adaptive Swing v2 — Phase62 native-format option L1 CSV and two detached source/receipt signatures

**DRAFT / offline research ONLY / stacked on Phase61 PR #66. Not a vendor-authentication system, real strategy backtest, or broker order authorization.**

## Gap being addressed

Phase61 rechecks the full original two-OOS-day, three-alternative-arm × 1W/2W/4W/8W source against an **owner-generated JSONL custody envelope** and pinned contract/master/calendar files. Anyone possessing the normalized source can fabricate the same envelope and matching hashes. It does not independently verify historical market L1 availability. Before a real vendor/exchange export can be considered, we need to demand its original format, map every row into the existing original OOS source and detect malformed or retrospectively changed records.

Phase22 already implements a strict native option Level-1 CSV parser. Phase62 **reuses that parser unchanged**, instead of silently adding a less strict, new CSV interpretation. The independently retained original CSV artifact, claimed publisher signature, claimed receipt-witness signature and manifest SHA pins are separately supplied bytes. **Neither signer key is externally trusted by this repo**: a user can generate both Ed25519 keys and all of these artifacts from the same synthetic option file.

## Offline cryptographic and source reconciliation

New `src/server/engine/ema15m/adaptivePhase62NativeCsvDualReceipts.ts` accepts:

- Entire original Phase61 source and pins. Its full **Phase60 → Phase59 → Phase58 → Phase57 → Phase51 → Phase50 → Phase8** evidence chain is re-audited. Original no-entry test sessions, all three alternative arms and four horizon buckets remain in denominator.
- One separately pinned raw **native-format CSV** of the original source top bid/ask option ticks. The exact required nine-column header is `sourceRecordId,sourceSequence,instrumentKey,eventAt,originalAvailableAt,bid,ask,bidQty,askQty`. Parsing uses Phase22's RFC4180-like strict parser (including quoted fields); all source sequences, record IDs, event and claimed availability timestamps, original instrument, BID, ASK and best-quote quantities must match the full Phase61 JSONL and Phase50 historical quote arrays **row for row and in original order**.
- One compact, SHA256-pinned manifest containing original CSV byte hash, Phase61 original JSONL/contract/catalog/calendar/licence-claim file hashes, the original event-time first/last timestamps, complete source row count, distinct claimed publisher/witness IDs, and claimed signing/witness receipt dates. Validation enforces a timestamp order and prespecified maximum claimed sign-to-receipt gap, but these timestamps remain **self-asserted and potentially post-hoc**.
- Two separately supplied **Ed25519 public SPKI DER keys**, independent SHA256 fingerprints and two **actual detached Ed25519 signatures over role-domain-separated complete manifest bytes**: `PUBLISHER` and `RECEIPT_WITNESS`. The public keys must be distinct and match separately pinned key hashes; the signatures must each be cryptographically valid under its respective key and match signed role-specific payload bytes. Merely pasting the publisher's signature into the receipt witness field, changing a CSV byte or editing the manifest after signing fails.
- Explicit SHA256 pins over exact original Phase61 input/pins, native CSV bytes, complete signed manifest and both public keys and signed receipt blobs. **Pins can be generated by the same operator; they do not certify vendor source, exchange identity or licence.**

Success status is `DESCRIPTIVE_TWO_CLAIMED_ED25519_SIGNATURES_AND_NATIVE_CSV_CONSISTENT_UNVERIFIED`, which establishes **mathematical signature and data consistency only**. It never means original NSE/BSE records have been independently authenticated. All `nativeExchangeOrVendorExportAuthenticated`, `independentlyLicensedHistoricalFnoL1Verified`, `independentSourceCaptureClockVerified`, `bestContractExpiryRecommendationAuthorized`, `originalNativeBrokerNrmlStopAckVerified`, `executionAuthorized` and `productionSafe` flags remain hard false; `nativeOrderInstruction=null`.

## Why the signatures do NOT prove original historical truth

A detached signature verifies that bytes were signed by *some* corresponding private key, not that the key is authorized by NSE, BSE or a licensed historical vendor. A claimed “timestamp” in a manifest signed after the OOS observation dates is **not proof that option BID/ASK was actually accessible to the trading strategy on those dates**, nor that contract expiry, order depth or vendor entitlements were authentic. A genuine future supplier package must be validated externally: original unmodified vendor-native transport, a trusted issuer/public-key registration and independently reviewed vendor historical data licence, archived strategy-side contemporaneous receive logs and official point-in-time exchange calendars/contracts. An opaque owner-signed document is not a substitute.

## Owner-private CLI usage

`scripts/audit-adaptive-phase62-native-csv-receipts.ts` takes two JSON dossiers, externally stored in owner-only `0600` files under `0700` private directories, with process-level network egress blocked by the operator:

```bash
npx tsx scripts/audit-adaptive-phase62-native-csv-receipts.ts \
  --approve-isolated-offline-review \
  --private-phase62-original-native-csv-package /private/phase62-source.json \
  --independent-phase62-csv-signer-pins /private/phase62-pins.json
```

The source file embeds an original native-format CSV as base64, the Phase61 dossier/pins, the signed manifest and only the PUBLIC Ed25519 key/signature bytes (no private keys). Output is **redacted aggregate counts only**: no option instrument keys, quotes, source paths, licences, raw CSV, PEMs or trading account information. A zero CLI exit signals only a descriptive software consistency check.
